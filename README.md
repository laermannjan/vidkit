# vidkit

Gets course and lecture video off the web into a media library: captures the streams,
downloads them, merges per-language voice-overs into one multi-audio file, corrects the
audio offset, tags, and files them.

## Where to start

| file | what it is |
|---|---|
| `SPEC.md` | what to build. Read first |
| `FINDINGS.md` | facts established by testing, not inference. Read before changing anything it covers |
| `prototype/` | a working capture panel. Reference implementation, not production code |

Build order is in `SPEC.md`. **Process first** - capture is built and proven, process is
unverified and holds every remaining unknown.

## Install

```sh
uv tool install git+https://github.com/laermannjan/vidkit
```

Needs `ffmpeg`, `mkvmerge` and `mkvpropedit` on `PATH`. `vidkit doctor` names what is
missing and how to install it.

## The prototype

Proves the capture design works. 79 checks across four suites:

```
prototype/run-tests.sh
```

It serves its own fixtures, so no setup. Needs `uv`; the scripts declare their own
dependencies and fetch a browser on first run (~90 MB).

To use it against a real page:

```
prototype/capture.py plan.tsv https://example.com/course
```

**What it is not:** a CLI, packaged, or structured for reuse. It is one script and one
injected panel, kept deliberately close to the thing it proves. Its plan format is a
generation behind `SPEC.md`. Port it in step 7; do not extend it in place.

## What is not built

Everything in `SPEC.md` under Process. Nothing has ever been run against a real
download, so `SPEC.md`'s two open questions are both measurements waiting to happen:
whether a captured `referer` still works an hour later, and how far apart real preambles
actually are.

## Repo conventions

**Trunk-based.** Short branches off `main`, squash-merged. The PR title becomes the
commit subject, so it is the title that must be a conventional commit - CI checks it.
Commits inside a branch are yours.

**CalVer, `YYYY.M.PATCH`.** Same month bumps the patch, a new month resets it to 0.
There is no public API to promise compatibility for, and `2026.9.1` tells you the one
thing you will want to know when a download breaks in eight months.

**Releasing.** A merge to `main` is not a release. A bot keeps a release PR up to date
with the version bump and the regenerated `CHANGELOG.md`. Merging that PR is the
release: CI then tags the merge commit and the tag push creates the GitHub Release.

`CHANGELOG.md` is generated by `git-cliff` and never hand-edited.

*Future idea, not built:* an editorialised summary on the GitHub Release itself, written
by a local model from the commit range and reviewed before it ships, with the mechanical
changelog left alone. mise does this with `communique`, which needs an API key in CI;
the local equivalent is `git log | claude -p` into a file the release workflow reads,
falling back to `git-cliff --latest` when the file is absent.
